# Track B DRBG and RBG Traceability

**Status:** Engineering baseline for CSTL pre-review; not a validation claim.  
**Selected candidate:** CTR_DRBG with AES-256 and the derivation function, subject to CMVP/CSTL confirmation.

## Decision rationale

Track B requires a complete random-bit-generation architecture rather than a range sampler that directly consumes host bytes. NIST SP 800-90A Rev. 1 specifies deterministic random-bit generation mechanisms based on hash functions or block-cipher algorithms [1]. The project therefore selects AES-256 CTR_DRBG with the derivation function as the initial engineering candidate because it provides a clearly specified deterministic mechanism, a conventional AES-based implementation target for x86-64, and a direct path to CAVP DRBG testing.

This is a candidate profile, not evidence that the current code is Approved. The exact DRBG capabilities, security strength, entropy input length, reseed policy, prediction-resistance policy, and CAVP certificate scope must be selected with the laboratory. The project must track any current CMVP Implementation Guidance update and the active Approved Security Functions list before submission.

## Required DRBG profile decisions

The following decisions must be made before implementation is treated as validation-grade:

1. Select the target security strength and confirm the corresponding AES-256 CTR_DRBG parameter set, including the exact seed length, entropy input requirements, nonce/personalization string policy, additional input policy, reseed interval, and prediction-resistance behavior.

2. Decide whether the entropy input is obtained from an external validated component, an OS-provided source justified under CMVP guidance, or a source that must be evaluated under SP 800-90B. The current `getrandom(2)` call alone does not answer this question.

3. Define whether the DRBG and range service share the same module boundary. The range transform must not make the output appear as an Approved algorithm if only the DRBG is approved.

4. Decide whether the implementation is pure software, uses a known processor algorithm implementation/accelerator, or has multiple processor-dependent variants. Every claimed variant must be included in the validation scope or excluded by the Security Policy.

5. Define the API lifecycle so that an uninstantiated, self-test-failed, integrity-failed, reseed-required, or zeroized context cannot service an Approved request.

## Implementation sequence

The first implementation increment should introduce a C11 context and state-machine skeleton without claiming Approved output. The context should use a provider interface so the current Linux source can be a testable engineering provider while the eventual validated entropy path is independently selectable. The next increment should implement and test AES-256 CTR_DRBG against known-answer vectors in C11. Only after the C11 vectors and state machine are stable should the AES and DRBG primitives be ported to YASM.

The existing public convenience function may remain as a non-Approved compatibility service during migration. A new Approved service should require an initialized context explicitly; this makes lifecycle, ownership, thread safety, reseeding, fork behavior, and failure latching auditable. The old TLS raw-entropy cache should not be used by the Approved service.

## Certification blockers

The following blockers prevent any FIPS claim today: no CAVP certificate, no Approved DRBG implementation, no entropy-source validation or accepted justification, no SP 800-90C construction mapping, no module Security Policy, no power-up/conditional self-tests, no image-integrity test, no final module boundary, and no CSTL assessment. Passing project unit tests, sanitizers, benchmarks, and Linux syscall checks does not remove these blockers.

## ACVP test boundary

The CAVP DRBG page publishes informal vectors and identifies DRBGVS as the validation testing requirement; NIST explicitly states that informal vectors do not replace CAVP validation [7]. The ACVP DRBG specification requires injected entropy and other inputs and exercises instantiate, generate, and reseed. It does not replace separate evidence for the entropy source, health tests, uninstantiate, automatic reseed, or error handling [8]. The harness must therefore retain both the vector runner and the independent lifecycle/fault tests.
